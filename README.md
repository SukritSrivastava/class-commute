# Class Commute

Tells students the best-timed Mumbai local train to catch from their home
station to reach college on time for a given class start time.

Given a home station, a college station, a class start time, and a buffer
(minutes you want free before class), it finds the **latest train that still
arrives by (class start − buffer)** — the one that cuts it closest without
being late — plus 2-3 earlier backup options.

## Tech stack

- Next.js (App Router) + TypeScript
- Tailwind CSS
- Data source: [RailRadar API](https://railradar.in) (`/v1/lookup/search/stations`,
  `/v1/trains/between/{from}/{to}`)
- Deploy target: Vercel

The RailRadar API key is only ever used server-side, in Next.js API routes
(`app/api/*`). The browser never sees it — the client calls our own
`/api/best-train` route, which proxies to RailRadar.

## Living inside 1,000 requests a month

The RailRadar free tier allows **1,000 requests a month and 10 a minute** —
about 33 a day for the whole user base. That makes the upstream call the
scarcest resource in the project, and most of the architecture is about not
spending one. Five layers, cheapest first:

1. **Bundled station list.** `lib/data/mumbai-stations.json` is generated by
   `npm run stations:refresh` and committed. Autocomplete searches it in the
   browser, so typing costs nothing — no debounce, no minimum query length,
   matches on the first keystroke. This replaced a request per typing burst,
   which was by far the largest drain.
2. **Edge cache.** `/api/best-train` is a GET so its response can be cached by
   the CDN; two students asking the same question share one invocation. The TTL
   depends on the answer: a *tomorrow* result is stable for hours, a *today*
   result decays as trains depart.
3. **In-instance timetable cache.** 6h TTL keyed `from:to:journeyDate`, with an
   in-flight map so concurrent identical requests make one upstream call.
4. **Rate limiting.** Per-IP sliding window on both routes, so a loop against
   the public endpoint can't drain the month.
5. **Graceful degradation.** Past 85% of the month, or whenever RailRadar is
   unreachable, a cached timetable is served with an "as of" timestamp rather
   than an error. A week-old locals timetable is very nearly correct; an error
   page is useless.

`GET /api/dev/quota` reports upstream usage by endpoint and day in development
(it 404s in production, because the counters are per-instance and would mislead).
Every upstream call is logged with its cache-hit status:

```
[railradar] UPSTREAM trains/between | month 1/1000 | today 1 upstream, 0 cached | BVI:CCG:2026-09-08
[railradar] CACHE    trains/between | month 1/1000 | today 1 upstream, 1 cached | BVI:CCG:2026-09-08
```

## Journeys with a change

RailRadar's `/trains/between` returns **direct trains only**. Ask it for
Borivali to CSMT and it answers with an empty list, because no such train
exists — you change at Dadar. That is a huge share of real Mumbai commutes, so
the app plans the change itself.

**How it knows a change is even possible.** `lib/network.ts` is a hand-authored
model of the network: which line each station sits on, and where the lines
meet. No API tells us this, and probing candidate interchanges to find out would
spend the month's quota on guesses. Dadar is two station codes — `DDR` on
Western, `DR` on Central — because it is two buildings sharing a footbridge, so
interchanges carry a code *per line*. A station missing from the model degrades
safely: no plan is found, and the app answers direct-only rather than inventing
a route.

**What it costs.** Three upstream calls: one to prove no direct train works,
then two legs. Never speculatively — the legs are only fetched after the cheap
answer has been tried and found wanting. It is affordable because the legs are
*hub* pairs: every Western-to-Central commuter produces some variation of
`… → DDR` and `DR → …`, so the leg cache converges far harder than end-to-end
pairs ever could. Measured against the live API: the first such journey costs 3
calls, an identical repeat costs 0, and a different Western-to-Central journey
reuses whichever leg it shares.

**Why a direct train usually wins.** Ranking on "latest departure" alone would
prefer an interchange leaving 08:10 over a direct leaving 08:00. That is wrong,
because the outcomes are not symmetric: leaving fifteen minutes earlier costs
fifteen minutes, while missing a connection costs the whole journey — you are
on the bridge at Dadar watching your train leave, and you are late. So an
interchange is scored as though it departed 15 minutes earlier than it does
(`INTERCHANGE_PENALTY_MINUTES`). It wins only when it is *substantially*
better, not marginally. Fifteen minutes is roughly one train's recovery in the
peak: the cost of the failure it risks.

Transfers default to 8 minutes and Dadar overrides to 10, because its change is
a staircase, a bridge and another staircase, and at 08:30 the bridge is the
bottleneck. Connections leaving more than 30 minutes on the platform are not
offered at all — that stops being a connection and starts being a wait.

**Known limits.** One change only: two changes on this network almost always
means a journey better served by another mode, and each extra leg doubles the
quota cost and multiplies the risk. And a journey *to* the far half of an
interchange (Borivali to Dadar Central) is answered as "no route" rather than
"ride to Dadar Western and walk over the bridge".

## Working without a network

People use this on platforms, where signal is unreliable — an app that needs
connectivity fails exactly when it is needed. Timetables barely change day to
day, so it doesn't have to.

- **The shell is precached.** A service worker (`app/sw.ts`, built by Serwist)
  precaches the app shell and its JS chunks — including the bundled station
  list — so the app loads and station search works with no connection at all.
- **Answers are saved on the device.** Successful `/api/best-train` responses go
  into IndexedDB keyed by route and journey date, alongside the moment they were
  fetched. Entries older than 7 days are evicted on open.
- **Saved answers are labelled, not disguised.** Offline, the last route returns
  its saved answer marked "Saved answer, as of 8 Sept, 9:26 pm."
- **No spinner that can't resolve.** Offline with nothing saved, the app says so
  immediately (~70ms) and says what to do about it.
- **Quiet freshness.** Opening the app online refreshes the last route in the
  background if the saved answer is more than 15 minutes old — never blocking
  first paint, and never on a first visit.

It is installable: `app/manifest.ts` plus a generated icon set
(`npm run icons:build`), with the `apple-*` meta tags iOS needs on top of the
manifest Android reads.

To verify the offline path end to end:

```bash
npm run build && npm start
RAILRADAR_ACCEPTANCE=1 PORT=3000 npx playwright test e2e/offline.spec.ts
```

## Project structure

- `lib/railradar.ts` — typed RailRadar API client, plus the cache, coalescing
  and stale-serving that sit in front of it
- `lib/bestTrain.ts` — the best-train matching/ranking logic (pure functions)
- `lib/time.ts` — every `Asia/Kolkata` concern, in one place
- `lib/stations.ts` + `lib/data/mumbai-stations.json` — the bundled station list
  and the client-side search over it
- `lib/cache.ts` / `lib/quota.ts` / `lib/rateLimit.ts` — the quota machinery
- `lib/schemas.ts` — zod request schemas with user-facing error copy
- `lib/format.ts` — small display-formatting helpers
- `scripts/build-stations.mts` — generates the station list (`npm run
  stations:refresh`); the only thing allowed to spend quota on station lookups
- `app/api/best-train/route.ts` — main matching endpoint (GET, edge-cacheable)
- `app/api/stations/search/route.ts` — station search **fallback only**; costs
  quota, and is no longer on the typing path
- `app/api/dev/quota/route.ts` — development-only usage report
- `app/sw.ts` — service worker source (built to `public/sw.js`)
- `app/manifest.ts` — web app manifest
- `lib/network.ts` — the line/interchange model of the suburban network
- `lib/journeys.ts` — ranking direct and one-change journeys against each other
- `lib/offlineCache.ts` — IndexedDB store of answered routes
- `lib/requestBestTrain.ts` — live / saved / honest-failure decision table
- `scripts/build-icons.mts` — generates the icon set (`npm run icons:build`)
- `components/StationAutocomplete.tsx` — accessible combobox for station input
- `components/BufferStepper.tsx` — buffer-minutes input
- `components/ResultCard.tsx` — train result card (best pick / alternative)
- `app/page.tsx` — the form + results page

## Setup

1. Install dependencies:

   ```bash
   npm install
   ```

2. Copy `.env.example` to `.env.local` and add your RailRadar API key:

   ```bash
   cp .env.example .env.local
   ```

   ```
   RAILRADAR_API_KEY=your_railradar_api_key_here
   ```

   Get a key at [railradar.in](https://railradar.in). The free tier allows
   1,000 requests/month and is rate-limited to **10 requests/minute** — the
   app surfaces a clear "please wait a minute" message if that limit is hit.

3. Run the dev server:

   ```bash
   npm run dev
   ```

   Open [http://localhost:3000](http://localhost:3000).

## Notes on the data

- RailRadar's station search matches against Indian Railways' literal
  (often abbreviated) station names — e.g. searching "Churchgate" won't
  match, but "church" does, since the real record is "BMBY CHURCH GTE". The
  autocomplete component handles partial/fuzzy queries fine; users should
  just pick from the dropdown rather than typing full names and pressing enter.
- RailRadar returns **HTTP 200 with an empty result**, not a 404, for a
  station code it doesn't recognize (it echoes the invalid code back as the
  station name). The app detects this and shows an "unrecognized station"
  message instead of a false "no trains found."
- Only stations tagged `city: "Mumbai"` are surfaced in autocomplete, to keep
  results relevant to the Mumbai suburban network (this also covers outer
  stations like Thane, Kalyan, Panvel, and Vasai Road). The generator keeps a
  station the seed list was explicitly aiming at even when RailRadar files it
  under its own municipality, so the outer termini are not lost.
- Because the railway's own names are abbreviations nobody types, the bundled
  list carries hand-written `aliases`: "vt", "cst" and "csmt" all find the same
  station, and "church gate" finds `BMBY CHURCH GTE`.

## Deploying to Vercel

1. Push this repo to GitHub (or GitLab/Bitbucket) and import it in the
   [Vercel dashboard](https://vercel.com/new).
2. In the project's **Settings → Environment Variables**, add:
   - `RAILRADAR_API_KEY` — your RailRadar API key (same value as in
     `.env.local`). Add it for all environments you plan to use
     (Production, Preview, Development).
3. No other configuration is needed — this is a standard Next.js App Router
   project, so Vercel's default build (`next build`) and Node runtime for the
   API routes work out of the box.
4. Deploy. Every push to the connected branch will redeploy automatically.
